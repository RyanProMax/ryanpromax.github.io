## 现状

AI Coding 最常见的问题，不是“模型不会写”，而是它会在不确定时主动补需求、在长任务里持续漂移、在看起来解释清楚时实际上没有做对。

所以我现在看 AI Coding，重点已经不再是“prompt 写得够不够花”，而是这三件事：

1. **上下文怎么给**
2. **任务怎么组织**
3. **结果怎么验收**

如果这三件事没设计好，再强的模型也只是在更快地产生不可控改动；如果这三件事设计好了，AI 才更像一个可协作、可约束、可验收的工程执行者。

## 1. 上下文怎么给

### 1.1 从 Vibe 到 Spec 到 Harness：三种 AI 编程范式

可以把 `Vibe -> Spec -> Harness` 写成三种“AI 编程范式”，但更准确地说，它们是三种**控制范式**：区别不在于工具，而在于你给 AI 多大自由度、多少约束，以及有没有闭环。

这不是一个严格的标准分类，而是我在实践里最有用的一套观察框架。

| 范式 | 本质 | 适合任务 | 你需要给 AI 的东西 | 主要风险 | 典型产出 |
| --- | --- | --- | --- | --- | --- |
| **Vibe coding** | 快速试探和迭代 | 小改动、原型、demo、低风险修补 | 明确边界、少量上下文、快速验证命令 | 容易漂移，容易把“跑起来了”误当成“做对了” | 一个可运行初版 |
| **Spec-driven execution** | 先收敛意图，再执行实现 | 中等复杂度功能、模块改造、替换依赖 | 目标、约束、非目标、验收方式 | spec 写得过重或过旧，会反过来污染上下文 | 一份设计工件 + 分步实现 |
| **Harness loop** | 把执行放进循环系统 | 长链路、高风险、跨模块、可持续推进的任务 | 任务拆分、外置状态、质量门、回滚点 | 没有质量门时，只会把错误自动化放大 | 一个可重复运行的执行闭环 |

我的经验是：

- **Vibe** 解决的是“我想先试试”
- **Spec** 解决的是“我到底要什么”
- **Harness** 解决的是“我怎么持续推进，而且不失控”

它们不是互斥关系，而是控制强度逐级上升。大任务通常不是“只用 Harness”，而是 **先用 Spec 收敛边界，再用 Harness 推进执行**。

再落到更实用的一层，可以这么选：

| 任务特征 | 推荐范式 | 原因 |
| --- | --- | --- |
| 范围小、验证快、失败成本低 | **Vibe** | 启动快，最适合先拿到可运行版本 |
| 已经超出一句话能说清的范围 | **Spec** | 先把目标和约束固定下来，避免 AI 补需求 |
| 跨模块、跨仓库、跨多轮会话 | **Spec + Harness** | 单次对话很难兜住，需要外置状态和质量门 |
| 一旦出错代价很高 | **Spec + Harness** | 重点从“会不会写”切换到“怎么验证和回滚” |

如果只用一句话概括：

> **AI Coding 的区别，不在于是不用 AI，而在于你让它处在哪种控制范式里。**

参考：

- [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- [Superpowers](https://github.com/obra/superpowers)
- [Ralph](https://github.com/snarktank/ralph)

### 1.2 Spec-driven execution：从 OpenSpec 到 Superpowers

`Spec-driven execution` 的核心，不是“多写文档”，而是**把稳定决策从聊天记录里拿出来**，让 AI 基于一个更可靠的中间工件执行。

这件事既可以做得很结构化，也可以做得很轻量。我觉得 `OpenSpec` 和 `Superpowers` 刚好代表了两个很典型的方向。

#### OpenSpec：结构化 spec 工件

[OpenSpec](https://github.com/Fission-AI/OpenSpec) 的思路，是给每个 change 建一套完整工件：`proposal`、`specs`、`design`、`tasks`，再配合 `propose -> apply -> archive` 这类流程，让需求、设计和实施都落在可审阅、可版本化的文件系统里。

这类方式的优点很明确：

- 适合多人异步协作
- 适合需求需要审阅、归档、回看
- 适合把“这次改什么、为什么改、怎么验收”留成长期工件

但它的代价也很明确：

- 前置结构更重
- 对小任务来说容易过度设计
- 如果团队不做裁剪，工件会很快膨胀

所以我更把 OpenSpec 看成一种**结构化上限**：它告诉你 spec 系统可以强到什么程度，但不代表每个任务都需要用满。

#### Superpowers：更自由的 spec 工作流

相比之下，[Superpowers](https://github.com/obra/superpowers) 更像一种**自由 spec 范式**。

它的重点不是固定目录，而是固定工作流：先澄清，再收敛设计，再生成执行计划。以它仓库里的 [`brainstorming` skill](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) 和 [`writing-plans` skill](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md) 为例，核心路径大致是：

```text
对话澄清 -> 收敛设计 -> 写短 spec -> 生成 implementation plan -> 执行
```

我更喜欢把这种方式当成 `Spec-driven execution` 的主线，原因很简单：

- 它允许 spec 先从对话里长出来
- 它更适合在真实项目里渐进收敛
- 它没有要求你先接受一整套固定目录
- 它更接近多数工程团队已经有的工作节奏

如果让我给一个实际建议，我会这样取舍：

- **团队协作、异步审阅、长期沉淀更重要**：偏 `OpenSpec`
- **日常开发、局部改造、强调灵活收敛更重要**：偏 `Superpowers`

也就是说，OpenSpec 更像“完整 spec 体系”，Superpowers 更像“轻量 spec 工作流”。

#### spec 也会变坏

很多人第一次引入 spec，会本能地觉得：“只要把东西都写下来，质量就会更高。”

现实通常不是这样。

spec 很容易在这四种情况下变坏：

1. **目标、历史决策、执行日志、聊天摘抄混在一起**
   一份文档同时承担“为什么做、要做什么、做过什么、聊过什么”，最后没有任何一层是清晰的。

2. **同一份文档同时承担对齐、追踪、复盘、备忘**
   一旦一个文件试图兼任所有角色，它就会越来越长，也越来越难被 AI 正确消费。

3. **旧 spec 不归档，信息开始腐烂**
   已经过期的约束和已经失效的设计仍然留在主文档里，AI 很容易把它们当成仍然有效的指令。

4. **补丁式追加，层次越来越乱**
   今天补一段、明天补一段，最后变成 append-only 大杂烩，人和 AI 都只会读到局部。

这也是为什么我现在不再把 spec 理解成“越全越好”，而是更强调**上下文卫生**。

我自己的精简原则是：

- 稳定约束单独放，比如架构约束、接口原则、公共约定
- 当前任务 spec 只写这次真正需要对齐的内容
- 执行记录、进度、实验结论另存，不要混进 spec 主文
- 任务结束后，要么归档，要么裁剪，不要把所有历史永久挂在主干上

一句话总结就是：

> **spec 的价值不在于“写得多”，而在于“把真正稳定且关键的东西，从聊天记录里提取出来”。**

#### plan mode 适合什么，不适合什么

`plan mode` 这一类能力，我更愿意把它理解成**会话级规划工具**，而不是 spec 系统本身。

它很适合：

- 把模糊需求拆成一版可执行路线
- 快速发现风险和依赖项
- 帮你把讨论收敛成一份设计草稿

但它不天然解决这些问题：

- 跨会话复用
- 多人异步审阅
- 长期版本化沉淀
- 任务结束后的归档与裁剪

所以更稳的用法不是“plan mode 替代 spec”，而是：

```text
对话澄清 -> plan 收敛 -> 固化成短 spec / 计划工件 -> 执行
```

### 1.3 不要一次性喂满上下文，让 AI 先澄清再执行

高质量的上下文，不是“用户预先写完所有细节”，而是**用户先给目标，AI 先补齐关键不确定项，再进入执行**。

如果一上来就让 AI 开始改代码，它最容易做的事情就是补需求。而一旦它开始补需求，后面所有“看起来合理”的实现都可能建立在错误前提上。

我现在更偏向把澄清过程固定成一个协议，至少先问清这五件事：

| 维度 | 要澄清的问题 |
| --- | --- |
| **目标结果** | 这次到底要交付什么，成功长什么样？ |
| **允许修改的边界** | 哪些文件、层级、模块可以改，哪些不要碰？ |
| **不变量** | 哪些接口、行为、数据契约必须保持不变？ |
| **验证方式** | 改完用什么命令、测试、截图或日志来证明？ |
| **停止条件** | 什么叫做“够了”，什么不属于这次范围？ |

如果 AI 没有主动问这五类问题，我基本会认为它还没准备好开始动手。

一个我觉得足够实用的输入模板是：

```text
目标：这次要完成什么
现状：当前已知的问题是什么
边界：哪些模块/文件允许改，哪些不要碰
不变量：哪些行为或接口不能变
验收：改完怎么验证
如果你不确定，请先追问，不要自行假设
```

另外，有几类任务我认为必须先追问，不能直接做：

- 跨模块修改
- 可能影响兼容行为
- 当前没有测试兜底
- 跨仓库接入
- 涉及 schema、协议、公共 API 调整

在这些情况下，AI 最不应该做的就是“先写了再说”。

## 2. 任务怎么组织

### 2.1 跨仓库协作：给 AI 一个最小集成上下文包

跨仓库任务最容易乱，不是因为代码难，而是因为**上下文天然不共享**。解决方式不是把两个仓库整包塞给 AI，而是给它一个最小集成上下文包。

这个上下文包至少应该包含：

- 上游仓库的版本或 commit SHA
- 目标方法的签名、入参、返回值、错误语义
- 一个最小可运行示例
- 本地下游仓库的接入点和 adapter 边界
- 明确的验证命令

我更推荐下面这 5 步流程：

1. **冻结上游版本**
   先明确这次接的是哪个 release、tag 或 commit，不要让 AI 一边查主干一边实现。

2. **提取外部契约和最小示例**
   不要让 AI 自己从整个仓库推断接口语义，最好先给出你认可的最小 contract。

3. **定义本地 adapter 边界**
   这次只允许改哪一层，哪些公共接口不能动，要提前说清。

4. **先补 contract / integration test**
   让验证标准先落地，而不是把“接成功没有”交给主观判断。

5. **再实现接入**
   这时 AI 面对的是一个明确 contract，而不是两个同时打开的代码宇宙。

如果任务特别复杂，当然也可以继续拆成 `Scout / Integrator / Verifier` 这类角色，但那是增强项，不是主流程。主流程的关键仍然是：

> **不要让 AI 同时消化两个仓库；要让它围绕一个明确契约工作。**

### 2.2 不要一条 prompt 干到底：checkpoint、回滚和 harness loop

长任务最危险的地方，不是“AI 会不会写”，而是**你看不见它什么时候开始偏，而且偏了之后很难拉回来**。

这也是为什么我越来越不相信“一条 prompt 跑到底”的做法。它在 demo 里很好看，在工程里通常意味着：

- 中间状态不可观察
- 错误会被连续放大
- 你不知道是哪一步开始偏的
- 你没有明确的回滚点

更稳的方式，是把任务切成带 checkpoint 的执行单元。每个单元至少要有：

- 这一步要交付什么
- 允许动哪些东西
- 用什么命令验证
- 失败时回到哪里

#### Harness loop 可以怎么理解

如果说 `Spec` 解决的是“边界先对齐”，那 `Harness` 解决的就是“长任务怎么持续推进而不失控”。

这里我觉得 [Ralph](https://github.com/snarktank/ralph) 是一个很好的例子。它不是单纯在说“多轮调用 AI”，而是在把执行做成一个循环系统。

Ralph 最值得拿来讲的有四点：

1. **每轮都是 fresh context**
   每次迭代都启动一个新的 AI 实例，不让单次上下文越滚越脏。

2. **任务必须足够小**
   它不是让 AI “实现整个 PRD”，而是每轮只挑一个足够小的 story。

3. **状态外置**
   记忆不靠会话本身，而是靠 `git history`、`progress.txt`、`prd.json` 这些外部状态。

4. **过了质量门才继续**
   typecheck、tests、质量检查通过之后，才允许把 story 标成完成并进入下一轮。

也就是说，Ralph 这类 loop 最重要的不是“自动连续跑”，而是：

> **把任务、记忆、验证和停止条件从聊天窗口里拿出来，放进一个可重复执行的系统。**

如果用一句更工程化的话来定义 `Harness loop`，我会写成：

> **Harness 不是“多开几个 agent”，而是“把执行放进一个有状态、有质量门、有回滚点的循环系统”。**

一个足够实用的简化版可以长这样：

```text
收敛 spec -> 拆成小任务 -> 每次只做一个任务 -> 跑质量门 -> 记录状态 -> 进入下一轮
```

这也是为什么我会把 `2.2` 和前面的 `Harness` 放在一起讲：checkpoint、回滚和质量门，不是补充细节，它们本身就是 harness 的一部分。

## 3. 结果怎么验收

### 3.1 Electron 场景：把验收压成三层

Electron 场景最能说明一个问题：**“能跑”不等于“可以合并”。**

因为 Electron 天然横跨主进程、渲染进程、preload、IPC 和宿主环境，所以我更推荐把验收压成三层：

1. **纯逻辑测试**
   能剥离出宿主环境的逻辑，尽量先在 Node / Vitest / Jest 层测掉。

2. **边界 / 契约测试**
   preload 暴露 API、IPC request/response、权限控制和错误处理，优先测契约而不是 UI。

3. **启动级 / E2E 测试**
   必须依赖 Electron 的部分，再交给自动化启动去覆盖。

Electron 官方文档已经给了比较清晰的路径：

- [Electron Automated Testing](https://www.electronjs.org/docs/latest/tutorial/automated-testing)
- [Playwright Electron API](https://playwright.dev/docs/api/class-electron)
- [WebdriverIO Electron](https://webdriver.io/docs/desktop-testing/electron/)

我对这部分的结论一直很简单：

> **不要把所有问题都丢给 E2E。能下沉到纯逻辑，就下沉；必须依赖 Electron，再用启动级自动化。**

### 3.2 CLI 和 MCP：按 inner loop / outer loop 分工

我现在更认同的表述，不是“CLI 比 MCP 更好”，而是：**CLI 和 MCP 解决的是不同层面的闭环问题。**

在本地编码和验收的 `inner loop` 里，CLI 通常更自然：

- 读代码
- 改代码
- 跑测试
- 看日志
- 修失败
- 再验证

这些动作本来就发生在终端里，所以 AI 接进来之后，很容易形成一个连续闭环。

而在跨系统协作、鉴权、租户隔离、审计治理的 `outer loop` 里，MCP 的价值会更明显：

- 权限边界更清晰
- 外部系统接入更统一
- 团队共享工具更容易治理

这也是为什么我很喜欢 CircleCI 那篇文章里 `inner loop / outer loop` 的划分，它比“谁更先进”这种争论有用得多：

- [MCP vs. CLI for AI-native development - CircleCI](https://circleci.com/blog/mcp-vs-cli/)

另外两篇文章也很适合拿来当补充视角：

- [Why CLI Tools Are Beating MCP for AI Agents - Jannik Reinhard](https://jannikreinhard.com/2026/02/22/why-cli-tools-are-beating-mcp-for-ai-agents/)
- [MCP vs CLI Use - Scalekit](https://www.scalekit.com/blog/mcp-vs-cli-use)

所以我的结论不是“CLI 打败 MCP”，而是：

- **本地开发和验收闭环，优先 CLI**
- **跨系统权限和团队治理，优先 MCP**

这两者更像分工，不像替代关系。

### 3.3 合并前五问

最后我会把 AI 结果的验收压成“五问”，因为“能跑”远远不够。

#### 第一问：静态检查过了吗？

- 编译通过了吗？
- lint 通过了吗？
- type check 通过了吗？

#### 第二问：功能真的对了吗？

- 主要路径可用吗？
- 边界输入可用吗？
- 错误处理符合预期吗？

#### 第三问：契约有没有被意外破坏？

- 外部接口有没有偷偷变掉？
- adapter、IPC、SDK 调用的语义有没有偏？
- 旧行为有没有悄悄回归失败？

#### 第四问：工程质量能不能 review？

- 抽象是不是清楚？
- diff 能不能被团队正常 review？
- 测试是在验证行为，还是只是在迎合当前实现？
- 有没有顺手带进一堆无关改动？

#### 第五问：这份改动值不值得合并？

- 有没有变更说明？
- 有没有风险点说明？
- 有没有回滚方式？
- 有没有明确哪些内容留到后续？

真正实用的验收标准，不是“写完了没有”，而是：

> **这份改动，作为团队代码，是否值得被合并。**

## 收尾

如果把今天的内容压缩成一句话，我会这样说：

> **AI Coding 的关键，不是让 AI 写更多代码，而是让它在正确的控制范式里工作，并且始终处在可验证、可回滚、可合并的闭环里。**

再落到最实用的一层，就是这三句话：

1. **上下文怎么给**：不要让 AI 直接补需求，要先澄清，再执行
2. **任务怎么组织**：不要一条 prompt 干到底，要拆任务、设 checkpoint、保留回滚点
3. **结果怎么验收**：不要只看能跑，要看契约、质量、风险和可合并性
